# Development readiness and resolved contracts

**Date:** 2026-10-29. **Scope:** planning and specification reconciliation; application implementation has not started. This document resolves engineering ambiguities under the user's request to make VentureLens ready for development. Product behavior remains governed by the product specification; technical contracts below refine the technical specification without weakening its invariants.

## 1. Ready to start means

Development can start from P01-T01 using synthetic data and existing local/CI PostgreSQL. A cloud account, a paid model, an approved production rubric, and a completed deployment are not prerequisites for that work. The implementation plan defines the work to obtain those later capabilities; it must not confuse unfinished implementation with a contradictory requirement.

All development defaults below are explicit. Provider activation, confidential-data onboarding, jurisdiction-specific scoring and release require their stated evidence. Missing evidence fails closed; no task may invent success. The owner-reviewable scoring candidate is in [rubric-review.md](rubric-review.md); it remains unapproved until an explicit owner decision is recorded. That is a product decision, not an engineering contradiction.

### 4.1 Exact shared boundary decisions

- Actor is server-derived `{userId, workspaceId, role, authVersion}`. Critical services re-read authorization in the committing transaction; no browser-supplied actor is trusted.
- Global lock order: Workspace → Assessment → AnalysisRun/Review head → dependent rows sorted by stable ID. Account mutations lock Workspace → affected Users sorted by ID. Never acquire Workspace after a child row. Retry serialization/deadlock at most three total attempts with bounded jitter, revalidating actor/version each attempt; no external I/O inside retry closure.
- Command idempotency keys are client UUIDs, scoped to workspace/actor/operation. Hash canonical validated payload. Same key+same hash returns same result; changed hash gives 409. HTTP records retained initially 24h; permanent run/attempt/successor relations provide additional durable guards. UI never automatically replays paid/purge/approval commands after uncertain failures.
- Canonical hashes use UTF-8 JSON with sorted object keys, preserved ordered arrays unless the schema explicitly declares a set, explicit schema version, decimal strings and UTC ISO instants. Preserve source raw strings byte-for-byte in their stored field; do not locale-normalize hash inputs. Exclude operational timestamps/random IDs from semantic content hashes unless part of the declared identity. Hash exact retained manifests, not regenerated current DTOs.
- Mutation response is the T §8 envelope. HTTP routes use its status mapping; actions return typed envelopes. Missing optional values are valid draft data, not 422. Unknown booleans are parsed strictly. Paginated reads default25/max100 with stable declared cursors and parent validation.
- Monetary analytical values are base-10 decimal strings bounded for `numeric(38,12)`. Use a dedicated worker-safe decimal implementation, never JavaScript Number or Prisma imports in domain. Scores compare integer evidence counts/rational thresholds before display rounding. An implementation dependency is selected/pinned/license-reviewed when this code is added, not fetched dynamically at runtime.
- Source deletionEpoch is checked at dispatch and publication. Early development supports synthetic epoch bumps for race tests before the purge UI exists; absence of purge feature never means absence of fencing.
- Production cannot load test fixture adapters or synthetic successful results by missing config. A fixture run is labeled synthetic in test artifacts/UI previews and cannot become a real approved report.
- Small local integration stores and fake transports have explicit test-only configuration. Every real upload/report asset read remains behind an application route; opaque keys are not authorization.
